# Web Push provider

The HTTP provider module exposes a `webpush` adapter behind the existing
`NotificationDeliveryProvider` port. It uses RFC 8291 `aes128gcm` single-record
payload encryption and VAPID ES256 authorization. The adapter is not enabled
automatically; the host must explicitly register provider code `webpush`.

## Subscription representation and persistence

The current shared `PushDevice` contract carries one opaque token (up to 4 KiB).
For this milestone, the WEB platform token is a serialized Push API subscription
JSON object containing `endpoint` and `keys.p256dh` / `keys.auth`. The existing
`PushTokenProtector` encrypts that complete string with tenant/recipient-bound
AES-GCM before JDBC persistence; the adapter parses it only after the worker
reveals it for delivery. Never put the subscription JSON in logs, audit records,
metrics, API responses, or plaintext database columns.

The subscription is validated as HTTPS, with no user-info or fragment. Query
components are retained because push-service endpoints may use opaque query
tokens. The P-256 public key must be a 65-byte uncompressed point and the auth
secret must be 16 bytes. Registration and refresh must use the existing
tenant/recipient ownership rules and encrypted-token repository.

This preserves the provider-neutral device and delivery contracts. A future
registration API may expose a typed subscription DTO; it must still persist the
serialized secret only through `PushTokenProtector`, and must not add plaintext
endpoint/key columns.

## Host security boundaries

- `WebPushVapidCredentialResolver` is host-owned. It must authorize the tenant
  and return the subject, short-lived signing key material, public key, and key
  expiry. Private VAPID keys are never stored or generated by this module.
- The host owns VAPID key provisioning, rotation, revocation, and secret-manager
  or KMS integration. The provider signs short-lived ES256 JWTs per endpoint
  origin; it does not persist JWTs.
- `WebPushEndpointPolicy` is host-owned and MUST enforce tenant policy plus
  DNS/IP-aware egress restrictions. It must reject loopback, private, link-local,
  multicast, reserved, and metadata-service destinations, and defend against
  DNS rebinding by enforcing the resolved destination at connection time or
  routing through a trusted egress proxy. A string/hostname allowlist alone is
  insufficient for arbitrary subscription endpoints.
- The HTTP client must disable redirects. Redirects are not followed, preventing
  a push service from redirecting a request to an internal address.
- Subscription endpoints, query tokens, public keys, auth secrets, VAPID JWTs,
  and provider response bodies must never appear in logs or error codes.

## Delivery behavior

- Payloads use RFC 8291 ECDH P-256, HKDF-SHA-256, AES-128-GCM, and the
  `aes128gcm` record framing.
- Requests carry VAPID authorization, `Content-Encoding: aes128gcm`,
  `Content-Type: application/octet-stream`, and a bounded TTL.
- 2xx is accepted; 404/410 permanently invalidate the subscription; 408/425,
  429, and 5xx are retryable; authentication and other 4xx responses are safe
  permanent failures.
- The worker's persisted provider affinity must be `webpush`; no automatic
  provider fallback is performed.

## Operational requirements

Before enabling this provider in production, implement and test the host-owned
endpoint policy against real DNS resolution and connection pinning/egress proxy
controls, connect VAPID keys to managed secret/KMS infrastructure, and ensure
browser registration submits the complete subscription JSON through the
existing encrypted push-device registration path. The module intentionally
does not claim that a generic hostname check alone prevents SSRF.
