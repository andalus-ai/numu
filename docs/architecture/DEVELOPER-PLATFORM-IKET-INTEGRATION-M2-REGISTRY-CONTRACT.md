# M2 — Developer Organization and Application Registry Contract

- **Status:** Proposed contract; source-backed ownership decision, not a claim of runtime implementation.
- **Repository:** `andalus-ai/numu`
- **Depends on:** M0 Developer Platform / Iket integration boundary and M1 source audit.
- **Related:** `ADR-003-reusable-capability-modules.md`, `DEVELOPER-PLATFORM-IKET-INTEGRATION-M1-AUDIT.md`, Identity and Tenancy capability contracts.

## 1. Outcome

Define the tenant-scoped developer organization and application registry that will later power the Numou developer portal and integrate with independent API gateways such as Iket.

This milestone deliberately establishes the ownership and behavioral contract before adding a new aggregate, Maven module, persistence schema, REST resource, or gateway adapter. The repository audit must identify the correct existing application and persistence owners before implementation.

## 2. Source-backed ownership decision

The current repository structure already provides the primary identity boundaries:

- Identity owns user identity and authentication-related identity use cases. Its README describes user, role/scoped assignment, federated authentication, SCIM, resource authorization, personal access tokens and service accounts.
- Tenancy is a platform-level bounded context. Its aggregator describes tenant lifecycle, membership, settings and provisioning; its domain POM describes Tenant, TenantMembership, TenantSettings and TenantProvisioning aggregates/events.
- The identity application POM describes CQRS use cases and the UserRepository/PasswordHasher ports. These POM and README descriptions are evidence of intended boundaries, not proof that every listed behavior is complete or production-verified.

**Decision:** A developer organization is a tenant context in the initial Numou model. Do not create a parallel DeveloperOrganization aggregate that duplicates tenant identity, membership, settings or lifecycle. A later external publisher/vendor identity may be modeled separately only if its ownership, lifecycle and cross-tenant semantics are demonstrated to differ from tenant membership.

Identity remains the subject authority. Tenancy remains the tenant and membership authority. The developer application registry owns application registration and application-specific lifecycle. It references tenant and actor IDs through public contracts; it does not own or mutate their aggregates.

## 3. Conceptual model

### 3.1 Developer organization

A developer organization is the tenant-scoped workspace in which authorized members register and administer applications.

The organization context is resolved from authenticated request/service context and verified membership. A tenant ID supplied in a request body, URL parameter or arbitrary header is a selector at most; it is never proof of access.

The registry must not maintain a second membership table or independently assign tenant roles. It asks the tenancy/authorization boundary to authorize the actor for the requested operation.

### 3.2 Application

An application is a registered integration identity owned by exactly one tenant.

Proposed stable fields:

| Field | Meaning | Rule |
|---|---|---|
| applicationId | Opaque stable identifier | Generated by the platform; immutable |
| tenantId | Owning tenant | Immutable after creation; never inferred from caller input alone |
| name | Human-readable label | Mutable under authorized update |
| slug | Tenant-local human-readable key | Normalized and unique within tenant; not an authorization token |
| description | Optional description | Bounded length; treated as untrusted text |
| status | Lifecycle state | Controlled state machine |
| createdAt / createdBy | Creation provenance | Server-authored |
| updatedAt / updatedBy | Last-change provenance | Server-authored |
| revision | Monotonic application revision | Used for optimistic concurrency |
| archivedAt / archivedBy | Optional archive provenance | Set only by archive transition |

Do not place secrets, API keys, client secrets, signing keys, gateway credentials, tenant membership roles, API product entitlements, or raw usage events on the application aggregate.

### 3.3 Environments

An application may have isolated environments, initially `development`, `staging`, and `production`.

Environment identity is scoped to its parent application. Each environment has its own lifecycle and security configuration reference. The registry must not assume that development credentials, gateway routes, quotas or callback destinations are safe to reuse in production.

An environment is not a separate tenant, and it does not change the application's owner. A future deployment may map environments to separate gateway clusters or projects without changing the domain contract.

Proposed fields:

- environmentId: opaque stable identifier;
- applicationId: immutable parent;
- key: stable environment key from a bounded platform catalog;
- status: provisioning/active/suspended/retired lifecycle;
- revision: monotonic configuration revision;
- createdAt/updatedAt and actor provenance;
- optional gateway binding reference, populated only by a later integration workflow.

The registry must not persist gateway-specific route objects or Iket structs as its domain model.

## 4. Application lifecycle

Initial application states:

- **PENDING** — registration accepted but not yet enabled for API access.
- **ACTIVE** — eligible for separately authorized product/subscription and credential operations.
- **SUSPENDED** — access is disabled; ownership and historical references remain.
- **ARCHIVED** — administratively retired and read-only except for permitted audit/export operations.

Allowed transitions:

| From | To | Command | Guard |
|---|---|---|---|
| PENDING | ACTIVE | ActivateApplication | Authorized tenant administrator; required policy checks satisfied |
| PENDING | SUSPENDED | SuspendApplication | Authorized administrator or security policy |
| ACTIVE | SUSPENDED | SuspendApplication | Authorized administrator or security response |
| SUSPENDED | ACTIVE | ReactivateApplication | Authorized administrator; security/policy checks satisfied |
| PENDING | ARCHIVED | ArchiveApplication | Authorized administrator; no active dependent resources |
| SUSPENDED | ARCHIVED | ArchiveApplication | Authorized administrator; dependent resources retired or explicitly handled |
| ACTIVE | ARCHIVED | Not directly allowed | Suspend first, then retire dependents and archive |

The lifecycle does not itself issue or revoke credentials. Credential lifecycle is a separate security capability and must be invoked through its public application contract. Suspending an application must trigger a durable revocation/reconciliation intent before the platform reports that all edge access has been disabled. If downstream enforcement is unavailable, expose the pending enforcement state and do not claim immediate global revocation.

Application names and slugs may be changed only through an authorized update command with revision checking. Application ownership transfer is not an ordinary update; it requires a dedicated audited transfer workflow, explicit acceptance by the receiving tenant, and defined treatment of credentials, subscriptions, usage records and gateway bindings. No implicit cross-tenant reassignment is allowed.

## 5. Authorization contract

Every command and query is tenant-scoped and authorized at the application boundary.

Required context:

- authenticated subject/actor ID;
- resolved tenant ID from trusted request context;
- correlation/request ID;
- authorization decision or a reference to the policy evaluation context;
- idempotency key for side-effecting commands where retries are possible.

Authorization requirements:

1. Resolve the actor from the authenticated security context. Never trust `createdBy`, `actorId`, `tenantId` or role fields supplied by a client.
2. Verify active tenant membership through the Tenancy/authorization public contract.
3. Evaluate operation-specific permission through the existing authorization boundary; do not duplicate role evaluation inside the registry.
4. Scope every repository read and write by tenant ID and resource ID. A resource ID alone is never sufficient.
5. Perform authorization before returning resource details, existence distinctions, counts, validation details or pagination metadata that could leak cross-tenant information.
6. Return a non-enumerating not-found/forbidden policy consistently for cross-tenant resource probes.
7. Re-authorize each operation; do not assume a prior portal page load grants later command access.
8. Service-to-service calls use an explicit service identity and least-privilege scope. They do not inherit an arbitrary browser actor or caller-supplied tenant header.
9. Administrative cross-tenant support access, if required, must be a separately audited privileged workflow with reason, actor, scope and expiry. It is not a normal registry query mode.

Suggested permission vocabulary (names are proposed, not asserted to exist in the current permission catalog):

- `developer.application.read`
- `developer.application.create`
- `developer.application.update`
- `developer.application.activate`
- `developer.application.suspend`
- `developer.application.archive`
- `developer.environment.manage`

Before implementation, reconcile these identifiers with the actual Numou authorization catalog and use its established naming conventions. Unknown permissions fail closed.

## 6. Command and query contract

The initial application service contract should expose use cases rather than persistence entities:

- `RegisterApplication`
- `GetApplication`
- `ListApplications`
- `UpdateApplicationProfile`
- `ActivateApplication`
- `SuspendApplication`
- `ReactivateApplication`
- `ArchiveApplication`
- `CreateApplicationEnvironment`
- `GetApplicationEnvironment`
- `ListApplicationEnvironments`
- `ChangeApplicationEnvironmentStatus`

Every command receives trusted actor/tenant/correlation context separately from its business payload. Commands that can be retried accept an idempotency key or use a documented equivalent. Queries require bounded pagination and deterministic ordering.

Proposed versioned HTTP shape for a future adapter (not an existing endpoint):

- `POST /developer/v1/applications`
- `GET /developer/v1/applications`
- `GET /developer/v1/applications/{applicationId}`
- `PATCH /developer/v1/applications/{applicationId}`
- `POST /developer/v1/applications/{applicationId}:activate`
- `POST /developer/v1/applications/{applicationId}:suspend`
- `POST /developer/v1/applications/{applicationId}:archive`
- `POST /developer/v1/applications/{applicationId}/environments`
- `GET /developer/v1/applications/{applicationId}/environments`

The HTTP adapter must derive tenant/actor context from authenticated middleware and pass it to the application service. Do not accept trusted context fields in JSON bodies.

## 7. Idempotency, concurrency and persistence invariants

- Registration requests support an idempotency key scoped to tenant and operation. Repeating the same key and equivalent request returns the original result; reusing it with a different request is a conflict.
- Idempotency records are durable for the documented retention window and committed atomically with the application creation result.
- Tenant-local slug uniqueness is enforced by a database constraint, not only an application pre-check.
- Every update/transition includes an expected revision (ETag/If-Match at HTTP boundary). Stale writes return a conflict and do not overwrite newer state.
- The repository API always requires tenant scope. Avoid unscoped `findById` methods in the application-facing port.
- A tenant cannot read or mutate another tenant's application even if it knows the opaque application ID.
- Creation, lifecycle transitions, environment changes and ownership transfer produce audit records with actor, tenant, action, target, timestamp, correlation ID and outcome.
- Durable integration intents use the existing outbox capability if its public contract fits; do not invent an in-memory callback as a substitute for durable delivery.
- Events include stable event ID, tenant ID, application ID, aggregate revision, event type/version, occurred-at time and correlation/causation references. Consumers deduplicate by event ID and preserve aggregate ordering where required.
- Retention and deletion are explicit. Archive preserves history and stable references. Hard deletion is not part of the initial developer portal lifecycle.

## 8. Events and integration boundary

Proposed versioned domain/integration events:

- `developer.application.registered.v1`
- `developer.application.profile-updated.v1`
- `developer.application.activated.v1`
- `developer.application.suspended.v1`
- `developer.application.archived.v1`
- `developer.application.environment-created.v1`
- `developer.application.environment-status-changed.v1`

Events are facts, not commands. They must not contain credentials, secret values, bearer tokens, API key material or unnecessary personal data.

Iket integration is deliberately downstream:

1. Registry command changes application state and writes audit/outbox intent transactionally.
2. A provisioning workflow reads the committed event and checks that the target environment and application remain eligible.
3. The Numou gateway adapter translates neutral desired state into the versioned Iket platform-neutral management contract.
4. Iket applies the desired state idempotently and returns a stable resource reference/revision.
5. Numou records the gateway binding and reconciliation result without storing Iket's private runtime model.
6. Reconciliation detects drift and retries transient failures; terminal failures become operator-visible and never silently mark provisioning complete.

No step may rely on Iket's current management API until its mandatory authentication, listener isolation and strict JWT requirements are implemented and integration-tested. No raw credential is sent in a provisioning event.

## 9. Separation from adjacent capabilities

| Concern | Owner | Registry relationship |
|---|---|---|
| User identity and authentication | Identity | References actor/subject IDs |
| Tenant lifecycle and membership | Tenancy | Reuses tenant and membership contracts |
| Resource authorization | Security/authorization capability | Authorizes every registry operation |
| Application registration and lifecycle | Developer Platform registry (owner/module to be confirmed) | Owns application/environment records |
| API product, version and subscription | API product/commerce capability (future milestone) | References application and tenant |
| Credential issuance, hashing, rotation and revocation | Security/Vault/credential capability (future milestone) | Stores references only |
| Secret material | Vault | Registry never stores raw secret material |
| Gateway routing and edge enforcement | Iket or another gateway | Receives translated desired state |
| Workflow orchestration | Gamelan | Coordinates long-running provisioning after protocol compatibility is verified |
| Billable usage and invoicing | Metering/Billing/Finance | Registry provides stable attribution references, not financial ledger ownership |

Do not place plans, quotas, scopes, products, raw API keys or billing balances on the application aggregate. These have distinct lifecycles and will be specified in later milestones.

## 10. Environment and security policy

- Production environment activation is a privileged transition and must be policy-gated.
- Development/staging/production credentials and callback allowlists are separate.
- Production callback URLs require HTTPS except explicitly approved local development profiles; redirects to private/link-local/loopback addresses must be blocked by the outbound callback delivery boundary to prevent SSRF.
- CORS is a browser policy, not authorization.
- Portal UI visibility does not imply API permission.
- Application metadata is untrusted input: validate lengths, normalize slugs, encode output and avoid interpreting descriptions as markup.
- Never expose gateway management credentials or internal control-plane URLs to browser clients.
- Audit and application events exclude secret values and credential fingerprints unless a narrowly justified, non-reversible fingerprint is required for operator correlation.
- Suspend/archive operations must define how dependent subscriptions, credentials, webhooks and gateway bindings are handled; they must not silently cascade destructive deletion.

## 11. Acceptance criteria for implementation milestone

The following are required before calling the registry production-ready:

- [ ] Confirm exact public Tenancy membership and tenant-resolution ports and their authorization semantics.
- [ ] Confirm the existing Identity authorization contract and permission catalog; avoid a second evaluator.
- [ ] Trace existing application/service-account/API client concepts across the repository and prove whether they can be reused or need a distinct developer application aggregate.
- [ ] Select the owning Maven reactor/module based on the source trace; do not add a new top-level reactor speculatively.
- [ ] Implement tenant-scoped repository ports and enforce tenant ID in all storage queries and unique constraints.
- [ ] Implement lifecycle aggregate invariants and transition tests.
- [ ] Implement application use cases with authorization-before-read and idempotent commands.
- [ ] Add persistence tests for tenant isolation, uniqueness races, rollback, optimistic concurrency and idempotent replay.
- [ ] Add API contract tests for pagination, non-enumerating cross-tenant behavior and stale revisions.
- [ ] Add transactional audit/outbox tests for lifecycle transitions.
- [ ] Verify suspend/archive behavior against credentials, subscriptions, webhook delivery and gateway reconciliation.
- [ ] Keep Iket provisioning feature-flagged/disabled until its management plane is hardened and independently verified.

## 12. Explicit non-goals

This milestone does not deliver:

- a developer portal frontend;
- OAuth authorization server or developer API keys;
- API product catalog, subscriptions, plans, pricing or quotas;
- Vault credential issuance/rotation;
- Iket route provisioning or management API calls;
- billing-grade metering;
- package marketplace or executable plugin installation;
- a second tenant, organization, membership, identity or authorization model.
